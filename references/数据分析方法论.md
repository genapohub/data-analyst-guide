# 数据分析方法论

> 本文档是 `data-analyst-guide` 技能的领域知识库。

---

## 一、场景识别

| 场景 | 名称 | 判断条件（满足任一） | 产出量 | 预估周期 |
|------|------|---------------------|--------|---------|
| 场景一 | 0→1 数据体系搭建 | 新产品、无埋点/无看板/无数据仓库 | 10-12类 | 4-8周 |
| 场景二 | 中大型分析需求 | 新增业务线分析、用户画像、归因分析 | 6-8类 | 1-3周 |
| 场景三 | 小分析/临时取数 | 单指标波动分析、运营活动复盘 | 2-3类 | 1-3天 |
| 场景四 | 数据基础设施升级 | 数仓重构、BI工具迁移、实时数仓建设 | 8-10类 | 4-10周 |
| 场景五 | 数据探索/洞察 | 新业务方向探索、用户行为模式发现 | 3-4类 | 1-2周 |

### 识别流程

```
是否全新产品/无任何数据基建？ → 是 → 场景一
    ↓否
是否数仓重构/BI迁移/实时数仓？ → 是 → 场景四
    ↓否
是否新业务方向探索/行为模式发现？ → 是 → 场景五
    ↓否
是否涉及新增业务线/用户画像/归因模型？ → 是 → 场景二
    ↓否
→ 场景三
```

## 二、场景一：0→1 数据体系搭建（12类产出）

### 埋点与采集
1. **埋点方案** — 事件设计（事件名/触发时机/参数定义）、属性定义（用户属性/事件属性/Item属性）、上报规范（SDK初始化/批量上报/离线缓存/丢包重试）
2. **数据采集方案** — SDK选型（神策/友盟/自研）、服务端打点（关键支付/订单等服务端事件）、日志收集（Nginx日志/业务日志/行为日志）
3. **数据字典** — 表结构定义、字段说明（类型/枚举值/默认值）、血缘关系（字段从哪个上游表计算而来）、版本管理（字段废弃/新增的版本记录）

### 数仓与ETL
4. **数据仓库架构** — 分层设计（ODS原始层→DWD明细层→DWS汇总层→ADS应用层）、各层职责边界、数据更新策略（实时/准实时/T+1）
5. **ETL方案** — 数据清洗规则（去重/格式标准化/异常值处理）、转换逻辑（UDF/SQL/Spark）、调度策略（Airflow/DolphinScheduler依赖DAG）、SLA（ODS→DWD < 2h、DWD→DWS < 4h）

### 指标与看板
6. **核心指标体系** — 北极星指标（唯一、可量化、与商业目标挂钩）、一级指标（≤5个）、二级指标（≤15个）、三级指标（按业务线拆解）、每个指标定义公式+数据源+更新频率+责任人
7. **BI看板设计** — 看板分层（高管概览/业务运营/专题分析）、布局规范（左上→右下阅读顺序）、图表选型（趋势折线/构成堆叠/分布直方/排名条形）、筛选逻辑（时间/渠道/版本/地区）、数据刷新策略（实时/小时/日）

### 实验与治理
8. **AB实验体系** — 分流策略（Hash分桶/分层互斥）、样本量计算（power=0.8, alpha=0.05）、显著性检验（T检验/卡方/Mann-Whitney）、实验报表模板（假设/指标/结果/决策）
9. **数据质量监控** — 完整性（每日上报量波动±10%告警）、准确性（关键字段空值率<1%）、及时性（ETL延迟>SLA告警）、一致性（跨表同指标差异<0.1%）
10. **用户标签体系** — 基础属性（性别/年龄/地区）、行为标签（活跃度/购买频次/偏好品类）、预测标签（流失概率/LTV预估/推荐候选）
11. **数据安全与权限** — PII脱敏规则（手机号/身份证/银行卡）、行级权限（仅看本部门数据）、审计日志（谁在什么时候查了什么数据）、导出审批流程
12. **数据治理规范** — 命名规范（表名`{业务域}_{层级}_{实体}_{周期}`）、生命周期（ODS 30天→DWD 1年→DWS 3年→ADS 永久）、版本管理（DDL变更走审批+回滚）

## 三、场景二：中大型分析需求（6-8类产出）

1. **分析需求澄清文档** — 业务背景、核心问题（一句话）、决策场景（结果用于什么决策）、预期产出形式、时间要求
2. **分析框架设计** — 假设驱动（列出3-5个可能假设）、MECE分解（互斥穷尽）、分析路径树（主问题→子问题→验证方法）
3. **SQL/取数方案** — SQL脚本（含注释+性能优化）、中间表设计、取数口径定义（时间范围/用户定义/排除条件）
4. **可视化分析报告** — 图表+文字解读、关键发现（3-5条）、置信度标注
5. **洞察与建议** — 可执行建议（做什么/不做什么/先做什么）、预期影响量化、风险提示
6. **用户画像/分层方案** — 分层维度选择、分层规则（RFM/行为聚类/生命周期）、各层特征描述、运营策略建议
7. **归因分析模型** — 归因方法选择（首次/末次/线性/时间衰减/数据驱动）、归因窗口期、渠道增量计算
8. **LTV/留存/漏斗专项** — LTV计算模型（历史法/预测法）、留存曲线拟合（幂函数）、漏斗各步转化率+流失原因分析

---

## 四、场景三：小分析/临时取数（2-3类产出）

1. **数据查询结果** — SQL+结果表+数据更新时间戳+取数口径说明
2. **波动归因结论** — 维度下钻（按渠道/版本/地区/用户群逐层拆解）、同期对比、异常点定位
3. **简短分析报告** — 现象→原因→建议（3段以内），附关键数据截图

---

## 五、场景四：数据基础设施升级（8-10类产出）

1. **现状评估与瓶颈分析** — 现有架构痛点量化（查询延迟/ETL耗时/存储成本/运维人力）
2. **技术选型方案** — 数仓引擎对比（ClickHouse vs Doris vs StarRocks）、BI工具对比（Tableau vs Metabase vs 自研）、实时框架对比（Flink vs Spark Streaming）
3. **数据迁移方案** — 迁移步骤（DDL+数据双写+校验+切换）、回滚方案（数据可逆）、数据校验规则（行数/校验和/抽样比对）
4. **新旧系统并行方案** — 双写策略、比对周期（≥2周）、差异处理流程
5. **性能容量评估** — 新架构QPS/查询延迟/存储预估、资源需求（CPU/内存/磁盘）、扩容计划
6. **数据血缘重构** — 现有血缘梳理、重构后血缘映射、影响面评估
7. **BI报表迁移清单** — 报表优先级排序、迁移工作量评估、验证清单
8. **团队培训方案** — 培训大纲、实操练习、考核标准

---

## 六、场景五：数据探索/洞察（3-4类产出）

1. **探索目标定义** — 业务问题、假设列表、探索路径
2. **数据探查报告** — 描述性统计（均值/中位数/分位数/标准差）、分布形态（偏度/峰度）、相关性矩阵
3. **假设验证报告** — 假设列表、验证方法、结论（支持/不支持/不确定）、置信度
4. **可视化洞察** — 关键图表+解读、意外发现标注、后续建议

## 七、数据分析通用规范

### 指标体系规范
- 北极星指标必须单一、可量化、与商业目标直接挂钩
- 一级指标≤5个，二级指标≤15个
- 每个指标必须有：定义公式、数据源、更新频率、责任人
- 指标命名遵循「业务域_对象_度量_聚合方式」格式（如 `order_amount_daily_sum`）
- 指标变更需走审批：改名→影响面评估→下游通知→双名并行→废弃旧名

### SQL/取数规范
- 复杂查询必须加注释（目的/逻辑/注意事项）
- JOIN前确认关联键的唯一性（`SELECT COUNT(*) vs COUNT(DISTINCT key)`）
- 聚合查询注意去重逻辑（COUNT DISTINCT vs COUNT）
- 时间范围统一使用闭区间 `[start, end)`
- 大查询加 `LIMIT` 防止意外全表扫描
- 输出结果必须包含数据更新时间戳
- 临时表命名：`tmp_{分析师姓名}_{日期}_{序号}`，用完即删

```sql
-- 示例：7日留存率计算
WITH first_active AS (
  SELECT user_id, MIN(event_date) AS first_date
  FROM dwd_user_event
  WHERE event_date BETWEEN '2026-08-01' AND '2026-08-07'
  GROUP BY user_id
),
retention AS (
  SELECT f.first_date,
         COUNT(DISTINCT f.user_id) AS day0_users,
         COUNT(DISTINCT CASE WHEN e.event_date = f.first_date + INTERVAL '7 day'
                             THEN f.user_id END) AS day7_users
  FROM first_active f
  LEFT JOIN dwd_user_event e ON f.user_id = e.user_id
  GROUP BY f.first_date
)
SELECT first_date,
       day0_users,
       day7_users,
       ROUND(day7_users * 100.0 / NULLIF(day0_users, 0), 2) AS retention_rate_7d
FROM retention
ORDER BY first_date;
```

### 可视化规范
- 趋势用折线图，构成用堆叠图，分布用直方图，排名用条形图
- 同一看板内统一配色（主色+辅色≤5种）
- 重要指标加同环比/Target线
- 图表标题说明「什么指标 + 什么维度 + 什么时间」
- Y轴从0开始（除非有明确理由）
- 图表不堆砌——一屏≤6个图表

### AB实验规范
- 最小样本量需提前计算（power=0.8, alpha=0.05）
  ```
  样本量公式（双侧T检验）：
  n = (Z_{α/2} + Z_β)² × 2σ² / δ²
  δ = 最小可检测效应（MDE）
  ```
- 分流均匀性检验（SRM check）：实验组/对照组样本量比例与预期偏差<1%
- 实验周期≥2个完整业务周期（通常≥14天）
- 多重检验需校正（Bonferroni: α/n, FDR: Benjamini-Hochberg）
- 记录实验文档：假设→设计→结果→决策→后续

### 数据安全规范
- PII数据（手机号/身份证/银行卡）必须脱敏：`138****1234`
- 数据导出需审批（谁导/导什么/用途/销毁时间）
- 离线数据仅可存储在加密设备
- 遵循最小权限原则（按角色/部门/项目授权）
- 分析结果不含原始PII数据，聚合结果需满足 k-anonymity（k≥50）

## 八、AI 工具使用建议

| 阶段 | AI 用途 | 注意事项 |
|------|---------|---------|
| 指标设计 | 从业务描述推导指标体系 | AI给的指标要验证是否可落地（有无数据源） |
| SQL编写 | 自然语言转SQL | AI生成的SQL必须人工审查JOIN和去重逻辑 |
| 数据探索 | 异常值检测/分布描述 | AI不懂数据口径，需告知字段定义和业务上下文 |
| 可视化 | 图表类型推荐/布局建议 | AI不懂业务阅读习惯，布局需人工调整 |
| 分析报告 | 从数据生成文字解读 | AI容易"数据搬运"不产生洞察，需补充业务判断 |
| 实验设计 | 样本量计算/假设设计 | AI不懂数据分布，需提供历史数据方差 |

## 九、产出质量检查清单

### 通用检查
- [ ] 场景判断正确并已确认
- [ ] 产出清单完整
- [ ] 取数口径明确（时间范围/用户定义/排除条件）

### 指标与埋点
- [ ] 指标体系完整且可落地（每个指标有数据源）
- [ ] 埋点事件覆盖核心用户路径
- [ ] 北极星指标唯一且与商业目标挂钩
- [ ] 指标命名遵循规范

### 数仓与ETL
- [ ] 数据仓库分层合理（ODS→DWD→DWS→ADS）
- [ ] ETL无死循环/无数据丢失风险
- [ ] 数据质量监控告警配置到位
- [ ] 数据字典完整可查

### 分析与实验
- [ ] 分析结论含可执行的业务建议（不只是"XX上升了"）
- [ ] AB实验方案满足统计学要求（样本量/周期/多重检验）
- [ ] 归因模型选择有理由
- [ ] 可视化图表类型正确、配色统一

### 数据安全
- [ ] PII数据脱敏到位
- [ ] 权限按角色/部门隔离
- [ ] 导出有审批流程

### 去AI味检查
- [ ] 分析结论不只有"XX指标上升/下降"——有"这意味着应该做什么/停止做什么"
- [ ] 指标定义不是"业内标准"的复制粘贴——每个指标和当前业务目标有明确的对应关系
- [ ] 至少有一处"这个数据看起来不正常，但我认为它实际上没问题，因为..."的判断
- [ ] 看板不是所有指标都放上去——有明确的北极星指标和与之对齐的 3-5 个关键指标

## 十、超越AI味：数据分析师的真知灼见

> AI 能跑 SQL 生成图表，但真正的数据分析师知道——数据从来不会自己说话，是你替它说话。

### 10.1 反AI数据分析决策五条

**1. 问对问题比写对 SQL 重要 10 倍**

- 错误做法: "这是上周的用户行为数据，请分析"
- 正确做法: "用户注册后 7 天内没有下首单的比例是 67%——为什么？是因为不知道能买什么？还是价格不合适？还是注册流程太复杂导致进来的用户质量差？三个方向分别用数据验证"

**2. 相关性 ≠ 因果性，但业务要的是因果**

- "活动期间 DAU +30%，但新增用户次日留存从 25% 跌到 12%（来的都是薅羊毛的）。建议下次活动加门槛——如首单后才给奖励"

**3. 指标要有"好/坏"的判断标准**

- "内容页停留 3.2 分钟 = 好（用户在看）。支付页停留 3.2 分钟 = 坏（用户在犹豫/遇到问题）。同一指标不同场景含义相反"

**4. 报表不是越多越好，是越少越有效**

- "北极星指标：首单转化率（从注册到首单 < 7 天的用户占比）= 33%。如果这个指标不涨，其他指标涨了也没意义。关键驱动指标仅 3 个"

**5. 数据不会骗人，但取数口径会**

- 必须明确统计口径：活跃用户定义、排除条件、和历史报表口径是否一致、和竞品公开数据口径的差异

### 10.2 数据分析师直觉检查清单

| 如果... | 那就... | 否则就是 AI 方案 |
|---------|---------|-----------------|
| 没有标注数据更新时间 | 补上 | AI 不关心数据新鲜度 |
| 留存率突然+20% | 先怀疑数据丢失 | AI 直接报喜 |
| 两组样本量差>5% | 先查SRM | AI 假设分流绝对均匀 |
| 结论是"建议持续关注" | 改成具体的行动建议 | AI 永远在"建议关注" |
| 指标定义只有公式没有口径 | 补全口径（谁算/不算/排除什么） | AI 不知道口径比公式重要 |

---

_数据分析师的价值 = 不是更快的 SQL，是更准的问题。_
